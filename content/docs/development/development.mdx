## Local development with start.sh

From the repository root, use the `start.sh` script to run the full stack (frontend, API, database) with hot reload:

```bash
./start.sh dev
```

- **Frontend** — http://localhost:5173  
- **API** — http://localhost:5000  

To stop the development stack:

```bash
./start.sh dev --down
```

Ensure `.env` is configured (see [Environment](/development/environment)). The script uses Docker Compose for the dev profile; the frontend and server run in watch mode so code changes reload automatically.

## Building for Production

```bash
./deploy.sh patch    # Increment patch version and deploy
./deploy.sh minor    # Increment minor version and deploy
./deploy.sh major    # Increment major version and deploy
```

Requires Docker Hub access for image push.

## GitHub Actions Workflows

| Workflow | Trigger | What it does |
|----------|---------|----------------|
| **E2E Tests** | Push or PR to `main` or `dev` | Runs web unit tests, then Playwright e2e tests (Docker test stack + dev server). Use a branch ruleset to require **e2e** before merging into `dev` or `main`. |
| **Tag Release** | Push to `main` | Reads the version from `web/package.json`, creates the `vX.Y.Z` tag if it doesn't exist, then calls **Release**. Merging a version bump to `main` is what ships a release. |
| **Release** | Push of tag `v*` (e.g. `v0.0.16`), or called by **Tag Release** | Runs unit tests, builds Docker images (push to Docker Hub), builds Tauri Android (AAB), macOS (DMG), iOS (IPA), creates GitHub Release with CHANGELOG body and uploads assets. Optionally uploads AAB to Google Play if configured. |

### GitHub Actions secrets

Configure these in **Settings → Secrets and variables → Actions**. See [iOS Signing Setup](https://github.com/alexwohlbruck/parchment/blob/main/docs/ios-signing-setup.md) for iOS certificate details.

| Secret | Required | Used for |
|--------|----------|----------|
| `DOCKERHUB_USERNAME` | Yes | Pushing Docker images |
| `DOCKERHUB_TOKEN` | Yes | Pushing Docker images |
| `APPLE_CERTIFICATE_BASE64` | Yes | iOS builds (code signing) |
| `APPLE_CERTIFICATE_PASSWORD` | Yes | iOS builds (code signing) |
| `APPLE_PROVISIONING_PROFILE_BASE64` | Yes | iOS builds (provisioning) |
| `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | No | Automatic AAB upload to Google Play (full JSON key) |
| `GOOGLE_PLAY_TRACK` | No | Play track: `internal`, `alpha`, `beta`, or `production` (defaults to `internal`) |
| `APP_STORE_CONNECT_API_KEY_ID` | No | Automatic TestFlight upload |
| `APP_STORE_CONNECT_ISSUER_ID` | No | Automatic TestFlight upload |
| `APP_STORE_CONNECT_API_KEY_CONTENT` | No | Automatic TestFlight upload |
| `E2E_MAPBOX_ACCESS_TOKEN` | No | E2E Tests — map-related tests when set |

## Releases (CI/CD)

**Version:** The app version lives in `web/package.json` and is synced to `server/package.json`, `web/src-tauri/tauri.conf.json`, and `web/src-tauri/Cargo.toml` by `deploy.sh`.

**Release notes:** `CHANGELOG.md` holds the current release only, in [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format — an `## [Unreleased]` section above the most recent `## [X.Y.Z] - DATE` one. It never grows beyond those two sections.

Entries are written **progressively**: when a user-facing change is complete, add a bullet under `## [Unreleased]` beneath `### Added`, `### Changed`, or `### Fixed`. Don't wait for release time — that's how things get forgotten. Skip internal-only work.

Cutting a release retitles `[Unreleased]` as the new version, drops the previous one, and opens a fresh empty `[Unreleased]` — all in the release commit. `deploy.sh` shows you the accumulated notes first and offers an edit pass, since entries are written one at a time and the release is the first chance to read them together.

Past release notes aren't kept in the file. They live in [GitHub Releases](https://github.com/alexwohlbruck/parchment/releases) and, for every tag, in git itself: `git show vX.Y.Z:CHANGELOG.md`.

All reads and rewrites of the file go through **`scripts/changelog.sh`** (`unreleased`, `latest`, `latest --plain`, `release X.Y.Z`) so the format lives in one place. It feeds the release PR description, the GitHub Release body, and the Google Play "what's new" text. Play's field is plain text capped at 500 characters and is truncated by whole entries, so put the notable changes first.

**How to cut a release:**

1. Run `./deploy.sh patch` (or `minor` / `major`) from `dev`. It bumps every version file, stamps the changelog, commits, and opens a PR to `main`.
2. Review and merge the PR.
3. **Tag Release** fires on the push to `main`, reads the version from `web/package.json`, creates the `vX.Y.Z` tag, and calls **Release** — which builds Docker images, Tauri Android (AAB), macOS (DMG), iOS (IPA), creates a GitHub Release with the newest changelog section as the body, and uploads artifacts. No manual tagging needed.

**Android versionCode / iOS build:** `deploy.sh` updates the app version everywhere and sets **Android `versionCode`** in `web/src-tauri/tauri.conf.json` for Play Store. iOS uses the same `version` for user-facing version and build number.

**Publishing to stores:**

- **Google Play (automatic):** Set secret **`GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`** (full JSON key). Optional **`GOOGLE_PLAY_TRACK`**: `internal`, `alpha`, `beta`, or `production`. Enable [Google Play Android Developer API](https://console.cloud.google.com/apis/library/androidpublisher.googleapis.com), create a service account, invite it in Play Console with release permissions, put the JSON in the secret.
- **App Store:** Download the `.ipa` from the GitHub Release and upload via [App Store Connect](https://appstoreconnect.apple.com/) (Transporter or Xcode), or automate with [fastlane](https://fastlane.tools/).

## iOS Deployment Setup

For automatic iOS builds and App Store deployment:

- **[iOS Signing Setup Guide](https://github.com/alexwohlbruck/parchment/blob/main/docs/ios-signing-setup.md)** — Configure Apple certificates and provisioning profiles
- **[iOS Deployment Checklist](https://github.com/alexwohlbruck/parchment/blob/main/docs/ios-deployment-checklist.md)** — Quick reference for releases

## Database Management

The database is initialized with PostGIS, spatial indexes, required permissions/roles, and a default admin user.

To seed with a custom user:

```bash
docker exec parchment-server bun run seed:dev "FirstName" "LastName" "email@example.com" "https://example.com/picture.jpg"
```

## Debugging

Development mode includes:

- **Hot reload** for frontend and backend
- **Bun debugger** at `ws://127.0.0.1:6499/debug` or https://debug.bun.sh/#127.0.0.1:6499/debug
- **Source maps** for TypeScript debugging
