title: Transit Routing
description: GTFS import and MOTIS transit routing in Barrelman.
---

Barrelman includes a transit routing pipeline that downloads GTFS feeds, imports
stop and route data into PostGIS, pre-computes walking transfers via GraphHopper,
and proxies transit itinerary requests to a co-deployed MOTIS instance.

---

## How it works

MOTIS runs in **transit-only mode** (`street_routing: false`). It loads GTFS data
and runs the RAPTOR algorithm for stop-to-stop routing. All street-level routing
(walking to/from stops) stays in GraphHopper, and Parchment's trip planner
composes the full trip.

```
Transitland API
  |
  v
download GTFS ZIPs
  |
  v
parse stops / routes --> PostGIS (gtfs_stops, gtfs_routes, gtfs_stop_routes)
  |
  v
find nearby stop pairs (ST_DWithin, 500m)
  |
  v
compute walking transfers (GraphHopper pedestrian point-to-point)
  |
  v
inject transfers.txt into each feed
  |
  v
MOTIS loads processed GTFS
```

## GTFS import

Run the import pipeline to download and process GTFS feeds:

```bash
bun run import:gtfs
```

Or via the shell wrapper:

```bash
./scripts/download-gtfs.sh
```

### What the import does

1. Fetches the feed list from Transitland for the configured region
2. Downloads each GTFS ZIP
3. Parses `stops.txt`, `routes.txt`, `agency.txt` from each feed
4. Imports stops (with PostGIS POINT geometry), routes, and stop-route
   associations into the database
5. Finds all stop pairs within 500 meters using a spatial self-join
6. Queries GraphHopper for walking time between each pair
7. Generates `transfers.txt` and injects it into each feed ZIP
8. The processed feeds are available to MOTIS on restart

### Region bounding boxes

- `nc` (dev): North Carolina — `(-84.5, 33.7, -75.3, 36.6)`
- `global` (prod): all Transitland feeds (no bbox filter)

## API endpoints

### `POST /transit/route`

Plan a transit trip via MOTIS.

**Request body:**

```json
{
  "fromLat": 35.2094,
  "fromLng": -80.8605,
  "toLat": 35.2271,
  "toLng": -80.8431,
  "time": "2026-01-15T08:00:00Z",
  "arriveBy": false,
  "numItineraries": 3
}
```

**Response:** MOTIS OTPAPI v2 itineraries adapted to Parchment format.

### `GET /transit/stops`

Find transit stops near a point.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `lat` | number | required | Latitude |
| `lng` | number | required | Longitude |
| `radius` | number | `500` | Search radius in meters |
| `limit` | number | `20` | Max results |

### `GET /transit/routes`

Get routes serving a specific stop.

| Parameter | Type | Description |
|-----------|------|-------------|
| `feedId` | string | GTFS feed ID |
| `stopId` | string | GTFS stop ID |

### `GET /transit/departures`

Upcoming departures at a stop, from the MOTIS timetable, enriched with route
colors from the GTFS database. Query a stop directly with `feedId` + `stopId`,
or search spatially with `lat` / `lng`.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `lat` / `lng` | number | required unless `feedId` + `stopId` given | Point to search near |
| `radius` | number | `150` | Search radius in meters |
| `feedId` / `stopId` | string | — | Query one stop directly, skipping the spatial search |
| `time` | string | now | ISO 8601 time to query from |
| `n` | number | `50` | Max departures per stop |
| `routeTypes` | string | — | Comma-separated GTFS `route_type` values the caller expects here |
| `windowMinutes` | number | — | Drop departures further out than this |
| `routeShortNames` | string | — | Keep only departures on these routes |
| `directionId` | string | — | Keep only departures in this GTFS direction (`0`/`1`) |

`routeTypes` fixes a mismatch that plain nearest-stop search gets wrong: the
first stop returned names the station and supplies its route list, but a ferry
landing's GTFS point sits at the end of the pier and an aerial tramway's out
under the cables — so an unrelated bus stop on the street outside is usually
closer. Stops served by a route of a listed type rank first and are searched out
to 400 m; everything else stays within `radius`.

The preference is a ranking, never a filter. Feeds mistype their routes — the
Roosevelt Island Tramway is published as a bus — so a nearby stop of any mode is
still returned when nothing matches the requested mode.

#### Bounding the board by time

`n` is a plain event count with no time bound, so the horizon it buys swings with
how often the service runs: 50 events is about 45 minutes at a subway platform
and five hours at a ferry landing. Pass `windowMinutes` to bound the board by
time instead — `n` then only has to be large enough to fill the window. Each stop
reports `hasMore` when runs exist past what came back, whether they were trimmed
by the window or cut off by `n`.

A stop with no service in the window comes back empty rather than reaching past
it. That keeps "nothing for hours" distinguishable from "nothing at all", which
is what lets a caller decide for itself whether to show the next run whenever it
is — without a dormant stop dropping a departure weeks out onto an otherwise
busy board.

#### Service dates

Each departure carries `serviceDate`, the GTFS service day it belongs to, parsed
from MOTIS's trip id. This is **not** always the calendar date it departs on:
GTFS files a 01:00 train under the previous day's service, published as a 25:00
stop time. At a station running all night, two departures three minutes apart can
carry different service dates:

```
20260815_24:49_5_…  → departs 01:00 Sat, service date 2026-08-15 (Friday)
20260816_00:29_5_…  → departs 01:03 Sat, service date 2026-08-16 (Saturday)
```

Group a UI by calendar date — that is what a rider reads off a clock — and use
`serviceDate` only to tell tonight's last run from tomorrow's first.

## Health check

The `/health` endpoint includes MOTIS status:

```json
{
  "status": "ok",
  "database": "connected",
  "motis": "ok"
}
```

- `status: "ok"` — database and MOTIS both reachable
- `status: "degraded"` — database up, MOTIS down (transit routing unavailable but other features work)
- `status: "error"` — database unreachable

## Database schema

The GTFS import creates four tables:

| Table | Description |
|-------|-------------|
| `gtfs_feeds` | Feed metadata (ID, name, URL) |
| `gtfs_stops` | Stops with PostGIS POINT geometry and spatial index |
| `gtfs_routes` | Routes with type, color, agency info |
| `gtfs_stop_routes` | Many-to-many: which routes serve which stops |

Tables are created automatically at startup via `ensureGtfsSchema()`.

## Docker setup

MOTIS is added as a service in `docker-compose.yml`:

```yaml
motis:
  image: ghcr.io/motis-project/motis:latest
  working_dir: /data
  volumes:
    - ./motis/config.yml:/data/config.yml:ro
    - barrelman-gtfs-data:/data/gtfs
  ports:
    - "8080:8080"
```

The MOTIS config at `motis/config.yml` disables street routing:

```yaml
import:
  paths:
    - gtfs/
```

The `barrelman-gtfs-data` volume is shared between the Barrelman API (which
writes processed GTFS feeds during import) and MOTIS (which reads them).
